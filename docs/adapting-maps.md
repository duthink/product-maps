# Adapting MAPS to Your Context

**Product MAPS** is the framework. **MAPS** is the four-step loop inside it (Mark, Align, Proceed, Sync).

MAPS is intentionally simple.
It is meant to be adapted—without losing the moves that make it work.

This document explains what can change and what should remain stable.

---

## What you can adapt freely

- Question wording
- Section order
- Level of detail
- Examples and prompts
- Domain-specific versions (growth, ops, education, etc.)

If a prompt doesn’t help your team think, change it.

---

## What must remain stable (the “compatibility contract”)

MAPS relies on four core moves:

1. Clarifying the starting point
2. Checking assumptions against reality
3. Choosing the next step with purpose
4. Responding to feedback intentionally

If an adaptation removes one of these, MAPS will weaken—even if the document looks better.

---

## Using MAPS in different contexts

MAPS works for:
- feature development
- new products
- internal tools
- process changes
- technical migrations

A Product Map should reflect the **decision at hand**, not the size of the initiative.

---

## Team vs individual use

MAPS works best when discussed together.
However, individuals can use it to:
- prepare for alignment meetings
- clarify thinking
- document reasoning

If used individually, review it with others before acting on it.

---

## A warning about over-customization

If every team creates a completely different version, shared language erodes.

Prefer:
- small adaptations
- documented changes
- shared examples

MAPS works best when it’s recognizable—even when adapted.

---

## Remember the goal

MAPS is not about compliance.
It’s about clarity.

If it helps you decide better, you’re using it correctly.
