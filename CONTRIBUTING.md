# Contributing to Product MAPS

Thank you for your interest in contributing to **Product MAPS**.

This project exists to help product teams think more clearly about what they’re building, for whom, and why.

Contributions are welcome—especially those grounded in real product work.

---

## Naming convention (important)

Use:
- **Product MAPS** for the framework (first mention in a doc/page)
- **MAPS** for subsequent mentions and for the four steps

Do not use dots (no “M.A.P.S.”), and do not write “MAPS (Product MAPS)” or “Product MAPS / MAPS”.

---

## What kinds of contributions are useful?

You don’t need to write code to contribute.

We especially value:

### Better questions
- Improving wording in the canonical Product Map template ([maps/product_map.md](maps/product_map.md))
- Removing prompts that feel redundant
- Adding prompts that surface blind spots

### Real examples
- Redacted Product Maps from real projects
- Domain-specific examples (B2B, fintech, education, internal tools)
- “This didn’t work and here’s why” stories

### Documentation
- Clarifying how teams actually use MAPS
- Explaining common failure patterns
- Writing short guides based on real usage

---

## How to contribute

1) **Start with an issue**
- Describe what you observed
- Explain what felt unclear, missing, or unnecessary
- Context matters more than polish

2) **Fork the repo**
- Make changes in a focused branch
- Keep changes small and intentional

3) **Open a pull request**
- Explain why you made the change, not just what you changed
- Link to any relevant issue or real-world experience

---

## Pull request checklist
- [ ] Linked to an issue (if appropriate)
- [ ] Small, focused change (one idea per PR)
- [ ] Documented why the change helps users
- [ ] License compatibility noted (see [LICENSE](LICENSE))
- [ ] If adding examples, include a short note about origin and redaction (if needed)

---

## Contribution principles

- **Clarity beats completeness**  
  Fewer strong prompts beat many weak ones.

- **Real usage beats theory**  
  Lived product work beats abstraction every time.

- **Frameworks should disappear in use**  
  MAPS should feel invisible when teams are using it well.

- **Avoid jargon**  
  If a PM or dev would roll their eyes, rewrite it.

---

## What we’re cautious about

- Turning MAPS into a rigid checklist
- Adding “process” that slows teams down
- Over-automating early
- Introducing language that feels moralizing instead of practical

If in doubt, open an issue first.
